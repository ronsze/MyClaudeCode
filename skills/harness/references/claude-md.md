# CLAUDE.md 작성법

목적: 프로젝트 CLAUDE.md를 공식 규격과 하네스 원칙에 맞게 작성한다.

## 파일 규격

- `./CLAUDE.md`: 팀 공유, 세션 시작 시 항상 로드. `./CLAUDE.local.md`: 개인용(.gitignore).
- 하위 디렉토리의 CLAUDE.md는 그 디렉토리의 파일을 Read할 때 지연 로드된다.
- `@경로` 임포트 가능(재귀 4단계). 백틱으로 감싸면 리터럴. HTML 주석(`<!-- -->`)은 컨텍스트에서 제외된다.

## 작성 규칙

- **200줄 미만 유지**: 초과하면 `.claude/rules/`나 스킬로 분리한다.
- **넣는 것**: 모든 세션에서 필요하고 변경 빈도가 낮은 것 — 빌드·테스트 명령, 컨벤션, 아키텍처 결정, "항상 X 한다" 규칙.
- **보내는 것**: 멀티스텝 절차 → 스킬. 특정 경로에만 적용 → rules. 강제가 필요한 규칙 → 훅 (CLAUDE.md는 권고일 뿐 강제하지 못한다).
- **검증 가능하게 구체적으로**: "깔끔하게"가 아니라 "들여쓰기 2칸"처럼 지켰는지 판정 가능한 문장으로 쓴다.
- **모순 제거**: 추가할 때 기존 규칙·다른 로드 파일(user CLAUDE.md, rules)과 충돌하는지 대조한다.

## 프로젝트 사실

my-claude-code 플러그인의 스킬·에이전트는 프로젝트 고유 값을 CLAUDE.md의 `## 프로젝트 사실` 절에서 항목 이름으로 찾는다. 절 이름과 항목 이름은 아래 표 그대로 쓴다 — 구성요소가 이름으로 찾는다. 해당 없는 항목은 적지 않는다(구성요소는 없는 항목을 묻는다).

| 항목 | 값 | 쓰는 곳 |
|---|---|---|
| 기본 브랜치 | 브랜치 이름 | implement ③, merge |
| 작업 브랜치 | 작업 브랜치 이름 형식 | implement ③ |
| 컴파일 명령 | 영향 모듈만 컴파일하는 명령 형태 | implement ③·④ |
| 빌드 명령 | 전체 빌드 | merge |
| 테스트 명령 | 전체 실행 형태와 클래스 필터 형태 | merge, test-engineer |
| 커밋 제목 | 제목 정규식 | merge |
| 잔류물 패턴 | 병합 diff에서 막을 패턴 | merge |
| 계약 | implement 수준 판정에서 계약으로 보는 것의 목록 — 프로젝트 아키텍처가 정한다 | implement |
| 코드 스타일 | 문서 경로 (있을 때만) | implement, code-reviewer |
| 아키텍처 | 문서 경로 (있을 때만) | implement, code-reviewer |
| 테스트 문서 | 문서 경로 (있을 때만) | implement, test-engineer |
| 스펙 위치 | 복합 수준 계획 파일을 두는 디렉토리 | implement ② |
| API 스펙 | 실제 응답 스키마를 확인하는 방법 | implement ① |
| 공용 UI | 공용 UI 컴포넌트 모듈 경로 | figma-matcher |
| UI 확인 | UI만 바뀐 변경의 확인 방법 | implement ⑥ |
| worktree 준비 | 새 worktree에 복사할 gitignore 파일 목록 | implement ③ |

## 템플릿

```markdown
# CLAUDE.md

## 프로젝트 사실

- 기본 브랜치: <이름>
- <위 표의 항목>: <값>

## <주제별 섹션>

- <항상 적용할 규칙. 판정 가능하게 구체적으로>
```

## 검증

- 분량: `wc -l CLAUDE.md`로 200줄 미만인지 확인한다.
- (시험) 준수: 새 세션에서 규칙이 적용되는 대표 요청 하나로 실제 지켜지는지 확인한다.
- 배치: 각 항목이 "모든 세션에서 필요한가"를 통과하는지 대조하고, 아니면 위 보내는 곳으로 옮긴다.
- 프로젝트 사실: 절·항목 이름이 표와 같은지, 플러그인 구성요소 본문이 참조하는 항목 이름이 표에 있는지 `grep -o '프로젝트 사실 \`[^\`]*\`'`로 대조한다.
