# diagnose

목적: 증상의 원인을 코드 수준에서 특정해 보고한다.

## 절차

1. **증상 확인** — 소스별 진입:
   - Crashlytics: 이슈·이벤트를 조회해 스택트레이스와 발생 조건(기기·버전·빈도)을 확보한다.
   - 제보: 재현 경로를 확인한다. 불명확하면 사용자에게 묻는다.
2. **원인 특정**: 스택트레이스·재현 경로를 코드로 추적한다. 원인을 특정하기 전에 수정하지 않는다 — 추측 수정 금지.
3. **보고**: 원인 위치(`파일:라인`), 발생 메커니즘, 수정안.
4. 수정까지 요청된 경우 implement로 이어간다 — 수준 판정부터 시작한다.

## 경계

- 대상: 증상의 원인 추적과 보고. 상위 이슈 훑기 같은 조사 전용 요청 포함.
- 비대상: 코드 수정(→ implement), 증상 없이 코드 범위를 훑는 점검(→ code-reviewer).

## 종료 조건

원인을 특정해 보고했거나, 조사 전용 요청이면 조회 결과를 보고하면 완료.

## 실패 시

재현·추적으로도 원인을 특정할 수 없으면, 확인한 사실과 배제한 가설을 보고하고 멈춘다. 추측으로 수정안을 내지 않는다.

## 검증

- 호출 적절성: "이 크래시 원인 찾아줘"(대상)와 "이 함수 리팩터링해줘"(비대상)가 description만으로 판별되는지 확인한다.
- (시험) 목적 달성: Crashlytics 이슈 하나로 원인 보고까지 실행해 보고 형식(위치·메커니즘·수정안)이 지켜지는지 확인한다.
