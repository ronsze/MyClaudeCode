# implement

목적: 코드 변경 요청을 수준에 맞는 단계 조합으로 수행한다.

프로젝트 고유 값(기본 브랜치·컴파일/테스트 명령·계약 정의·스펙 위치 등)은 프로젝트 CLAUDE.md의 `## 프로젝트 사실`에서 읽는다(항목 이름은 harness 스킬 `references/claude-md.md`). 어느 단계에서든 필요한 항목이 없으면 추측하지 않고 사용자에게 묻고, 답을 CLAUDE.md에 추가하자고 제안한다.

## 단계

① 요청 접수 → ② 계획 → ③ 작업 환경 → ④ 구현 → ⑤ 리뷰 → ⑥ 테스트 → ⑦ 기록

모든 작업이 모든 단계를 거치지 않는다. ①~②에서 수준을 판정해 단계를 취사선택한다.

## 수준 판정

판정 축은 **새 계약이 생기는가**다. 계약 = 프로젝트 사실 `계약`에 나열된 것. 나열이 없으면 모듈 밖에서 보이는 public 시그니처와 외부에 노출되는 인터페이스(API·스키마·진입점)로 본다.

| 수준 | 기준 | 적용 단계 |
|---|---|---|
| 탐색 | 산출물이 코드가 아니라 답인 요청 — "되나?", "가능한가?", "대충 확인만". 코드를 써도 버린다 | ④ — 결과는 답·추천으로 보고, 코드는 커밋하지 않고 폐기를 명시 |
| 경미 | 결과가 지시에 이미 특정된 지점 변경 — 문구·값·경로·단순 스타일 | ④ |
| 경계 내 | 로직 변경이 있으나 계약이 추가·변경되지 않음. 호출부가 하나뿐인 신규 헬퍼는 계약으로 보지 않는다 | ②(채팅) ④ + 컴파일·셀프 리뷰 |
| 표준 | 계약이 추가·변경되지만 그 변경이 한 모듈의 public 시그니처 안에 머묾. 기존 모듈 안의 새 진입점, 호출부가 여럿이어도 시그니처가 그대로인 공용 코드 수정이 여기다 | ②(채팅) ④ ⑤ ⑥ |
| 복합 | 새 모듈이 생김, 또는 계약 변경이 둘 이상 모듈의 public 시그니처에 걸침(공용 타입·함수 시그니처를 바꿔 다른 모듈이 따라 바뀜), 또는 디자인 시안·외부 스펙을 참조해 구조를 새로 잡음 | 전 단계 |

판정이 갈리면 상위 수준을 택한다. **판정 결과는 착수 전에 "수준: 경계 내 — 근거 한 줄" 형태로 첫 줄에 말한다** — 사용자가 뒤집을 지점이다. 탐색 결과를 남기자는 요청은 새 요청이므로 다시 판정한다. ⑦ 기록은 수준과 무관하게 요청된 경우에 수행한다.

**독립적으로 계약을 갖는 단위가 둘 이상이면 먼저 분할을 합의한다.** 요청이 서로 독립적인 기능·진입점 묶음을 여럿 담고 있으면 세부를 파고들기 전에 그 사실을 먼저 말하고, 단위와 구축 순서를 합의한 뒤 단위별로 다시 판정한다. 하나의 계획에 전부 담으려 하지 않는다.

**구현 중·구현 후에 결과물이 바뀌면 계획이 근거다.** 계획 파일이 있으면 파일을, 없으면 ②에서 합의한 내용을 채팅에서 갱신해 확인받은 뒤 결과물을 고친다.

**재판정은 어느 단계에서든 일어난다.** 판정 시점에 없던 계약 변경이 드러나면(경계 내인데 공개 필드가 필요해짐, 표준인데 새 모듈이 필요해짐 등) 그 자리에서 멈추고 상향 재판정해 여기로 돌아온다. 올라간 수준의 적용 단계를 ②부터 다시 밟고 사용자와 합의한다. "거의 다 했으니 마저 한다"로 수준을 유지하지 않는다. 판정은 올라가기만 하고 내려가지 않는다.

## 추측 금지

주어진 컨텍스트로 정확한 판단이 불가능하면 추측으로 메우지 않고 사용자에게 묻는다. 모든 단계에 적용된다.

- 판정 기준: 해석이 둘 이상 가능하고 해석에 따라 산출물이 달라지면 묻는다. 해석이 갈려도 산출물이 같으면 묻지 않고 진행한다.
- 리포·프로젝트 문서·스펙(API 문서·디자인 시안)에서 확인 가능한 사실은 묻기 전에 먼저 확인한다. 확인해서 얻을 수 없는 것만 묻는다.
- 질문은 모아서 한 번에 하고, 답에 의존하지 않는 부분은 먼저 진행한다. 답을 받기 전에 그 부분을 구현하지 않는다.

## 단계 정의

1. **요청 접수**: 요구 내용을 확정한다. 이슈 트래커 카드가 지목되면 해당 스킬(Trello면 trello)로 조회해 내용을 가져온다. 새 API 연동이나 DTO 변경이 포함되면 프로젝트 사실 `API 스펙`이 정한 방법으로 실제 응답 스키마를 확인한다. 완료 후 후속 작업(커밋·카드 댓글 등)은 첫 요청에 명시됐거나 완료 시점에 요청된 것만 수행한다.
2. **계획**: 수준에 따라 형태가 다르다. 어느 수준이든 합의 후 착수하며, 이 계획이 이후 단계의 근거다 — 후속 단계의 수정은 계획과 대조해 수행한다.
   **합의되지 않으면 어디로 돌아갈지는 반려 사유가 정한다.** 접근 자체가 반려되면 방향 합의부터 다시 하고(복합은 계획 파일을 새로 쓴다), 접근은 유지한 채 내용이 반려되면 계획만 고쳐 다시 제시한다. 반려된 접근은 계획 파일의 `이외 고려 사항`에 이유와 함께 적는다. 합의 없이 ③으로 넘어가지 않는다. 계획을 제시하는 턴은 도구 호출 없이 끝낸다 — 사용자 응답을 받기 전에 같은 턴에서 ③ 이후로 이어가지 않으며, 계획 요지에 대한 세부 답변은 승인이 아니다.
   - **경계 내**: 채팅에 접근·수정 파일·검증 방법을 3~5문장으로 제시한다. 파일을 만들지 않는다.
   - **표준**: 채팅에 수용 조건 / 테스트 케이스 / 파일별 작업 / 회귀 대상 4개 절을 제시한다. 테스트 케이스는 수용 조건마다 `테스트명(프로젝트 테스트 문서의 함수명 형식) — 입력 — 기대 결과` 한 줄로 적고, 실패 경로(외부 호출 실패·빈 결과·잘못된 입력·권한 없음 중 해당하는 것)를 포함한다. 단위 테스트 대상 코드 변경이 없으면 `테스트 케이스: 없음`. 프로젝트 사실의 문서 항목(`코드 스타일`·`아키텍처`·`테스트 문서`) 중 관련 문서가 있으면 참조 문서로 함께 적는다. 파일을 만들지 않는다.
   - **복합**: 검토할 만한 대안이 둘 이상 있을 때만 먼저 채팅에서 방향을 합의한다 — 사용자가 접근을 고른 뒤에 계획 파일을 쓴다. 대안이 실질적으로 하나면 그 사실과 근거를 계획 파일 `확정 사항`에 적고 설계 제시로 바로 간다. 방향이 뒤집히면 설계 파일 전체가 폐기되므로, 방향 합의를 설계 제시에 흡수하지 않는다. 프로젝트 사실의 문서 항목 중 관련 문서가 있으면 참조 문서로 계획에 적는다. 디자인 시안이 Figma에 있으면 figma-matcher에 노드와 작업 모듈 경로를 위임해 요소별 재사용·확장·신규 판정을 받아 계획에 반영한다. 영향 범위 조사는 메인 세션이 직접 한다. 둘 이상의 모듈을 훑어야 해 출력이 커질 때만 Explore 에이전트에 위임한다.
     계획 파일은 두 번에 나눠 쓴다. (1) `references/plan.md`를 읽고 그 구조로 `<프로젝트 사실 스펙 위치>/<topic>-design.md`를 만들되 `## 설계` 절까지만 쓰고 멈춘다. 코드베이스 탐색은 이 단계에서 끝낸다 — 실행 절이 쓸 것까지 여기서 확인해 둔다: 계약이 닿는 인터페이스의 구현체·호출부·테스트 대역, 신규 의존성의 선언 위치, 검증 명령이 모듈 종류별로 다르면 어느 것인지. `자기 대조(설계)`를 수행해 지적을 고친 뒤, 미해결 항목과 함께 사용자에게 제시해 승인을 받는다. 승인 전에 `## 실행` 절을 쓰지 않는다. (2) 설계가 승인되면 같은 세션에서 같은 파일에 `## 실행` 절을 이어 쓴다 — 새로 탐색하지 않고 설계 단계에서 확인한 사실을 그대로 쓴다. 확인하지 않은 사실이 필요해지면 탐색하지 말고 `미확인`으로 적어 미해결로 낸다. `자기 대조(실행)`를 수행해 제시한다. 두 제시 모두 도구 호출 없이 턴을 끝낸다. 계획 리뷰는 사용자가 하며 서브에이전트에 위임하지 않는다.
3. **작업 환경**: 지시가 있으면 그대로 따른다. 지시가 없으면 묻지 않고 규칙으로 정한다 — 현재 브랜치가 프로젝트 사실 `기본 브랜치`면 작업 브랜치(프로젝트 사실 `작업 브랜치` 형식, 없으면 `feature/<주제>`)를 만들어 옮기고, 아니면 현재 브랜치에서 작업한다. 탐색 수준은 브랜치를 만들지 않는다. 결정은 첫 줄의 수준 판정 옆에 `브랜치: <이름>`으로 적는다.
   worktree를 새로 만들면 두 가지를 바로 한다. (1) 프로젝트 사실 `worktree 준비`에 나열된 gitignore 파일을 리포 루트에서 복사한다 — 새 worktree에 없어 빌드·MCP 호출이 실패하는 파일들이다. (2) 영향 모듈의 컴파일(프로젝트 사실 `컴파일 명령`)을 백그라운드로 실행해 둔다 — 설정·의존성 해석이 ②·④ 준비와 겹쳐 끝나게 한다. ④ 착수 전에 그 결과를 확인하고, 실패면 환경 문제로 보고 구현을 시작하지 않는다.
4. **구현**: 착수 전에 계획을 다시 읽고 지금도 유효한지 대조한다 — 지목한 파일·심볼이 실재하는지, 합의 이후 코드가 바뀌지 않았는지. 우려가 있으면 구현을 시작하기 전에 제기한다. 그 뒤 계획이 지목한 문서를 읽고 계획 기반으로 수행한다. 계획 없는 수준(탐색·경미)이면 프로젝트 사실 `코드 스타일` 문서(있으면)만 보고 지시 그대로 수행한다. 탐색은 답을 얻는 최소 비용으로만 만들고 결과 보고에 폐기 대상임을 적는다.
   - **경계 내 검증**: 영향 모듈을 컴파일해 통과를 확인하고, diff를 code-reviewer의 로직·재사용 기준으로 직접 훑는다. 서브에이전트에 위임하지 않는다.
5. **리뷰**(표준 이상): code-reviewer에 위임한다 — 위임 메시지에 점검 범위, 변경 성격에 맞는 기준, 그리고 판정 근거로 ②의 수용 조건·비목표(복합은 계획 파일 경로)를 담는다. 계획 테스트 케이스 절의 `리뷰 확인` 줄은 점검 항목으로 위임 메시지에 그대로 넣는다. 근거를 메시지에 담는 이유는 리뷰어가 문서 전문을 다시 읽지 않게 하기 위해서다. 발견은 계획과 대조해 처리한다: 상은 수정하고, 중은 수정안을 사용자에게 제시해 합의하고, 하는 보고만 한다. 계획과 어긋나는 방향이면 계획을 갱신하고 사용자에게 알린다.
6. **테스트**(표준 이상): 단위 테스트 대상 코드 변경이 있으면 test-engineer에 위임한다 — 영향 범위는 클래스 목록으로 지정하고(모듈 지정은 영향이 모듈 전반에 걸칠 때만), ②에서 합의한 테스트 케이스 목록과 수용 조건(복합 수준은 계획 파일의 `수용 조건`·`테스트 케이스` 절 그대로)을 함께 넘긴다. test-engineer는 그 케이스를 그대로 구현하며 케이스를 새로 고르지 않는다. 위임 메시지에 `검증 범위: <클래스 목록>`을 적는다. 완료 보고에는 test-engineer가 반환한 실행 명령 원문과 그 명령이 돌린 범위의 결과만 낸다 — 모듈 전체 통과 수 같은 범위 밖 수치는 적지 않는다. 보고에 실행 명령이 없거나 명령의 범위가 위임 범위보다 넓으면 재위임한다. 보고의 케이스별 결과를 계획과 대조해, 구현되지 않은 케이스가 있으면 사용자에게 알린다. 계획의 `수동 확인` 줄은 위임하지 않고 완료 보고에 `수동 확인 N건 — 확인 주체: 사용자`와 절차를 그대로 옮긴다 — 위임 범위에서 빠진 조건이 조용히 사라지지 않게 한다. UI 표시만 바뀌었으면 위임하지 않고 컴파일 + 프로젝트 사실 `UI 확인` 방법으로 대체한다. 최종 게이트다.
   ⑤와 ⑥이 둘 다 필요하면 한 메시지에서 동시에 위임한다. ⑥의 실패 수정이 생기면 그 변경분만 재리뷰한다.
7. **기록**: 커밋, 이슈 트래커 완료 댓글(해당 스킬), 작업 보고서 작성. PR을 만들 때 `.github/PULL_REQUEST_TEMPLATE.md`가 있으면 본문은 그 절 구성을 그대로 채운다 — `gh pr create --body`는 템플릿을 자동 적용하지 않아 비워두면 체크 항목이 통째로 빠진다. 복합이면 커밋 메시지 본문에 계획 파일 경로를 적고 설계 설명을 반복하지 않는다 — 스펙이 설명을 대체한다. 리뷰 발견 중 반영하지 않은 것은 스펙의 `이외 고려 사항`에 이유와 함께 적는다. 소요 시간은 사용자가 시작·종료 시각을 준 경우에만 적는다 — 모델은 요청 시각을 관측할 수 없으므로 추정하지 않는다. 토큰 사용량도 추정하지 않는다.

## 경계

- 대상: 프로젝트 리포의 코드 변경과 그 검증·기록.
- 비대상: 통합 병합·배포(→ merge), 코드를 바꾸지 않는 점검·문서 작업, 하네스 수정(→ harness).

## 종료 조건

판정된 수준의 적용 단계를 모두 마치고 결과를 보고하면 완료.

## 실패 시

계획과 실제가 어긋나 진행이 불가능하면(참조 부재, 전제 불일치) 우회하지 않고 멈추고 사용자에게 묻는다.

## 검증

- 호출 적절성: "버튼 문구 바꿔줘"(대상)와 "이 코드 설명해줘"(비대상)가 description만으로 판별되는지 확인한다.
- 프로젝트 사실: 본문이 참조하는 항목 이름(`계약`·`기본 브랜치`·`작업 브랜치`·`컴파일 명령`·`코드 스타일`·`아키텍처`·`테스트 문서`·`스펙 위치`·`API 스펙`·`worktree 준비`·`UI 확인`)이 harness `references/claude-md.md`의 항목 표에 전부 있는지 대조한다.
- (시험) 수준 판정: 대표 요청 여섯 개("이 API 페이징 되나?" / 문구 수정 / 기존 기능의 동작 조건 추가 / 공개 모델 필드 추가 / 기존 모듈 안 신규 진입점 / 공용 타입에 필드 추가)로 판정이 표와 일치하고(마지막은 복합), 판정이 착수 전 첫 줄에 말해지는지 확인한다.
- (시험) 추측 금지: 값·대상이 특정되지 않은 요청("여백 좀 늘려줘")에서 임의 값으로 진행하지 않고 묻는지, 리포에서 확인 가능한 사실은 묻지 않고 확인하는지, 프로젝트 사실에 없는 항목을 추측으로 메우지 않고 묻는지 확인한다.
- (시험) 상향 재판정: 경계 내로 시작한 작업에 계약 추가를 요구하는 조건을 끼워 넣어 구현 중 멈추고 재판정한 뒤 ②부터 다시 밟는지 확인한다.
- (시험) 계획 우선 수정: 구현을 마친 뒤 결과물 변경을 요청해, 계획을 먼저 갱신하고 그 다음에 결과물을 고치는지 확인한다.
- (시험) 미승인 경로: 제시한 계획을 접근 단위로 한 번, 내용 단위로 한 번 반려해 각각 방향 합의·계획 수정으로 돌아가는지 확인한다. 계획을 제시한 턴이 도구 호출 없이 끝나는지도 확인한다.
- (시험) 2단계 게이트: 복합 작업 하나를 시작해 설계 제시 턴 시점의 계획 파일에 `## 실행` 절이 없고, 승인 후 실행 절을 쓰는 턴에 새 탐색(Read·Grep·Explore) 호출이 없는지 확인한다. 대안이 하나뿐인 요청에서는 방향 합의 턴 없이 `확정 사항`에 근거를 적고 설계 제시로 가는지 확인한다.
- (시험) 테스트 케이스 계획: 표준 작업에서 ②에 테스트 케이스 절이 나오고, ⑥ 위임 메시지에 그 목록이 그대로 들어가는지, `수동 확인` 줄이 위임 메시지에는 없고 완료 보고에는 있는지 확인한다.
- (시험) 요청 분해: 독립 기능 둘을 한 요청에 담아 세부 질문 전에 분할을 먼저 제안하는지 확인한다.
- (시험) 기본 브랜치: 기본 브랜치에서 경미 수준 요청을 넣어 묻지 않고 작업 브랜치를 만들며 첫 줄에 `브랜치:`가 나오는지 확인한다.
- (시험) 목적 달성: 표준 이상 작업 하나를 실제 수행해 계획→구현→리뷰→테스트 흐름이 계획을 근거로 이어지는지, ②가 특정한 참조 문서를 ④가 실제로 읽는지 확인한다.
- (시험) 비용: 경계 내 작업 하나를 실제 수행해 서브에이전트 위임 없이 끝나는지 확인한다.
- (시험) 워크트리 준비: 새 worktree로 표준 작업을 시작해 파일 복사와 백그라운드 컴파일이 ② 전에 실행되는지 확인한다.
- (시험) PR 본문: 템플릿이 있는 리포에서 PR을 하나 만들어 본문이 템플릿의 절 구성을 갖추는지 확인한다.
- (시험) 검증 범위: 클래스 3개 변경을 표준으로 수행해 완료 보고의 명령이 그 클래스로 필터돼 있고 전체 스위트 수치가 없는지 확인한다.
