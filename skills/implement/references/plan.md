# 계획 문서 작성법

목적: 복합 수준 작업의 계획을 역할이 다른 세 문서로 남긴다. 경계 내·표준 수준은 계획 문서를 만들지 않는다 — `SKILL.md`의 ② 계획 참조.

**세 문서는 한 번에 완성하는 것이 목표가 아니다.** 검토하고 다음 단계로 진행하면서 부족한 것과 확정된 것을 가려 문서를 채워 가고, 그 과정을 거쳐 문서와 기능을 함께 완성한다. **불완전해도 되지만 대충 써도 되는 것은 아니다.** 쓴 내용은 확인한 사실과 확정된 결정만으로 정확하게 쓰고, 모르는 것은 추측으로 채우지 않고 `미결 사항`에 드러낸다. 불완전함은 빈 곳이 보이는 상태이지, 흐릿하게 쓴 상태가 아니다.

## 문서와 역할

기능 하나마다 프로젝트 사실 `스펙 위치` 아래 `<기능>/` 디렉터리에 세 문서를 둔다. 항목이 없으면 위치를 묻는다. 디렉터리 이름은 소문자 snake_case다. 작업 완료 후에도 삭제하지 않고 코드와 함께 커밋한다.

| 문서 | 역할 | 작성 기준 |
|---|---|---|
| `spec.md` | 기능명세. 사용자 관점에서 기능이 무엇을 보여 주고 어떻게 동작하는지 — 보여 줄 정보와 그에 필요한 것, 조작, 규칙, 예외 | 구현 방법(호출 방식, 저장, 계산 방법, 데이터 구조)과 시안으로 확인되는 화면 배치·모양·고정 문구를 쓰지 않는다 |
| `design.md` | 플랫폼과 무관한 구현 방식 | `spec.md`와 이 파일만으로 어느 플랫폼에서든 같은 동작을 만들 수 있어야 한다 |
| `plan.md` | 이 리포에서의 구현 계획 | 무엇을 어떤 순서로 고치고 어떻게 검증하는지 판단할 수 있어야 한다 |

**세 문서는 차례로 이어져야 한다.** `spec`을 보고 `design`을, `spec`과 `design`을 보고 `plan`을, `plan`을 보고 실제 구현을 할 수 있어야 한다. 사실 확인(외부 API·기존 코드)은 다음 문서를 쓰는 사람이 하고, 결정은 앞 문서에 있어야 한다. 다음 문서를 쓰다가 앞 문서에 빠진 결정을 발견하는 것은 실패가 아니다 — `작성 순서와 반려`의 보완 흐름으로 앞 문서를 고친다.

- **`spec`과 `design`을 가르는 기준**: `spec`은 구현 방법을 정하지 않지만, 구현 방법을 정하는 데 필요한 제품·운영 결정은 모두 정한다. 사용자에게 보이지 않아도 기획이 정해야 하는 것(새 데이터를 언제 받는지, 무엇을 기록하는지 등)은 `spec`이다. `spec`에는 결과로 쓴다 — "캐시한다"가 아니라 "그 사이에 다시 들어오면 앞서 본 날씨를 보여 준다". 그 결과를 어떻게 만드는지는 `design`이다. 문서의 숫자는 왜 있는지 본다 — 제품 결정이면 `spec`에 쓰고, 외부 자료의 한계(외부 API가 주는 범위 등)면 `spec`에는 사용자가 겪는 결과만 쓰고 숫자는 `design`에 쓴다.
- **결과와 방법을 나눈다**: `spec`은 결과만, `design`은 그 결과를 만드는 방법만 쓴다. `spec`의 정책 규칙에는 P번호를 붙이고, `design`의 규칙은 자기가 구현하는 P번호를 표시한다.
- 문서는 그 기능의 현재 동작을 담는다. 이후 작업이 기능을 바꾸면 해당 문서를 먼저 고치고 `변경 이력`에 남긴다. 기능·정책이 바뀌면 `spec`, 구현 방식이 바뀌면 `design`, 리포 안의 구조·배치가 바뀌면 `plan`이다.
- 이 구조 이전의 단일 계획 파일(`<스펙 위치>/<topic>-design.md`)은 작성 시점의 기록이므로 이관하지 않는다.

## 검증 항목의 세 단계

| 문서 | 항목 | 쓰는 것 |
|---|---|---|
| `spec.md` | 수용 조건 A | P·E 한 줄로는 드러나지 않는 확인 장면만 쓴다 — 경계값(정각, 범위 끝), 여러 규칙이 엮인 경우, 순서나 시간이 있는 경우, 시안으로 보이지 않는 동작. P·E 문장을 장면으로 바꾸기만 한 행은 쓰지 않는다. 판정 기준은 "이 행이 없으면 리뷰어가 놓칠 장면인가"다 |
| `design.md` | 필수 검증 항목 V | 설계 로직 검증. A로 드러나지 않는 설계 규칙의 분기·경계와, 사용자가 확인할 수 없는 P(예: 다시 묻지 않는 동작)를 검증한다. 후자는 그 P번호를 표시한다. A를 다시 쓰지 않는다. 테스트 이름·플랫폼 용어를 쓰지 않는다 |
| `plan.md` | 테스트 케이스 | 사용자가 확인할 수 있는 P·E, 그리고 모든 A·V를 빠짐없이 받아 단위 테스트·`수동 확인`·`리뷰 확인` 중 하나로 잇고, 구현에서 생기는 케이스를 더한다. 줄마다 `[P번호]`·`[E번호]`·`[A번호]`·`[V번호]`·`[구현]` 태그 |

P·E·A가 로직 테스트로 바로 확인되면 `plan`이 그것을 단위 테스트로 잇는다 — 같은 내용의 V를 만들지 않는다.

## 나누기 (선택)

기본은 기능 하나에 문서 셋이다. 아래 두 경우에만 나눈다.

- **`design` 부분 분할**: `design.md`가 한 번에 읽기 힘들고, 공유 계약만 알면 각 부분을 따로 구현·검증할 수 있을 때. `design.md`에는 개요와 `공유 계약`만 남기고 부분은 `design/<부분>.md`, 같은 부분의 구현은 `plan/<부분>.md`에 둔다. `spec`은 나누지 않는다. 나눌지는 `design`을 처음 제시할 때 사용자가 정한다.
- **기능 트리**: 진입점·사용자 목표가 다른 기능 여럿을 묶을 때. 상위 디렉터리에 조합용 `spec.md`(구성 표와 전체 흐름)를 두고, 기능 사이에 공유 계약이 있을 때만 상위 `design.md`를 둔다. 하위 기능은 각자 문서 셋을 갖는다.

두 경우 공통 규칙:

- 공유 계약·공통 규칙·외부 자료 링크는 그것을 쓰는 단위들의 공통 최하위 조상에 둔다. 한 단위만 쓰면 그 단위 문서 안에 둔다. 나중에 쓰는 단위가 늘면 새 공통 최하위 조상으로 옮기고 원래 자리에는 `사용 계약`만 남긴다.
- 형제 단위끼리는 참조하지 않는다. 자식은 조상의 `공유 계약` 항목만 가리키고, 상위는 하위의 경로와 책임 한 줄만 적는다.
- 단위 하나를 구현할 때 읽는 범위는 자기 문서와 `사용 계약`에 적은 항목뿐이다.
- 계약에는 소비하는 쪽이 받는 것만 쓴다: 용어, 입력, 출력 타입, 결과 구분(`결과 \| 조건 \| 소비하는 쪽이 받는 것`, 실패는 원인을 빠짐없이), 관찰 가능한 부수 효과, 호출 특성. 만드는 쪽의 내부 조건은 만드는 쪽 문서에만 둔다.
- 상위 `spec.md`의 전체 흐름에는 단계와 담당만 쓴다. 조건·분기·실패 처리는 담당 단위 문서에만 둔다.

## 공통 작성 선

**모든 문서는 사람이 읽는다. 가독성이 다른 모든 작성 규칙보다 우선한다.** 에이전트는 절 이름으로 필요한 내용을 찾을 뿐이므로, 에이전트를 위해 사람의 가독성을 희생하지 않는다.

- **분량 상한을 두지 않는다.** 짧게 만들려고 규칙·값·문구·순서를 빼거나 뭉뚱그리지 않는다. 구현에 필요한 정보는 전부 적는다.
- 완결된 문장으로 쓴다. `A·B → C / D` 같은 기호 나열이나 약칭으로 압축하지 않는다.
- 한 줄에는 정보 하나만 담는다. 조건·결과·이유를 한 줄에 몰아넣지 않는다.
- 표는 여러 항목을 같은 축으로 비교할 때만 쓴다. 설명을 표 셀에 욱여넣지 않는다.
- **한 규칙은 한 곳에만 쓴다.** 같은 문서에서는 절 이름으로, 다른 문서는 P·A·V 번호나 `사용 계약`으로 가리킨다.
- **열어 본 것만 적는다.** 기존 동작·파일·심볼·외부 스펙은 확인한 뒤 적는다. 확인하지 못했으면 `미확인`으로 적는다.
- **미루지 않는다.** 문서를 읽거나 코드를 보면 정해지는 것은 지금 정해 본문에 쓴다. 지금 정할 수 없는 것만 `미결 사항`에 `[차단]`(구현 전에 정해야 함) 또는 `[비차단]`(구현 후 정해도 됨)을 붙여 적고, 누가 정하는지 쓴다. "적절히 처리", "구현 시 결정", `TBD`를 남기지 않는다.
- **민감 정보는 사용자 확인 후에만 쓴다.** API 키·토큰·계정 정보·내부 주소 같은 값을 문서에 적어야 하면 쓰기 전에 사용자에게 확인을 요청한다. 확인 전에는 원문 대신 값이 있는 위치만 적는다.
- **외부 자료 링크는 `외부 자료` 절에만 모은다.** `자료 \| 링크 \| 쓰는 곳` 표로 쓰고, 본문은 자료 이름으로 가리킨다. 시안·기획 문서는 `spec`, API 문서·원본 데이터 출처는 `design`에 둔다.
- 각 절은 지우지 않는다. 해당 없으면 `해당 없음` — 빈칸은 누락과 구분되지 않는다.
- 절 이름은 템플릿 그대로 쓴다. code-reviewer·test-engineer 위임이 절 이름으로 내용을 찾는다.

## spec.md

**화면은 시안이 정본이다.** 배치·모양·고정 문구는 `외부 자료`의 시안 링크로 가리키고 글로 다시 쓰지 않는다. `spec`에는 무엇을 보여 주는지, 언제 보여 주는지, 보여 주려면 무엇이 필요한지만 쓴다.

**결정과 현재 동작을 구분한다.** 이미 있는 기능을 문서로 옮길 때, 결정된 적이 확인된 것만 `정책 규칙`·`목표가 아닌 것`에 쓴다. 코드의 현재 동작일 뿐 결정 여부를 모르는 것은 `미결 사항`에 현재 동작과 함께 적는다.

**한 내용은 한 곳에만 쓴다.** 정상 흐름의 규칙은 `정책 규칙`(P), 정상이 아닌 경우의 규칙과 보이는 것은 `예외 처리`(E), 보이는 정보와 그 표기 규칙은 `보여 줄 정보`가 정본이다. `사용자 흐름`과 `쓰는 기존 앱 기능` 표는 조건·결과를 다시 쓰지 않고 P·E 번호로 가리킨다. `수용 조건`은 검증 시나리오라서 결과를 문장으로 쓰되 `근거` 열에 정본 번호를 적는다.

| 절 | 내용 | 판정 기준 |
|---|---|---|
| 작성일 | `YYYY-MM-DD` | 제목 바로 아래 |
| 요약 | 첫 줄에 기능을 한 문장으로 정의하고, 이어서 무엇을·왜를 다섯 줄 안팎의 목록으로 | 이 절만 읽고 기능이 무엇인지 말할 수 있어야 한다 |
| 배경 | 해결하는 사용자 문제, 기존 동작과 그 문제, 이전 시도 | 방향 합의를 생략했으면 대안이 하나뿐인 근거를 여기 적는다 |
| 목표 | 기대 결과 목록 | 완료 후 성공 여부를 판정할 수 있는 문장이어야 한다 |
| 목표가 아닌 것 | 관련 있으나 의도적으로 하지 않는 것 | 인접 기능·인접 정리를 적어 범위를 막는다 |
| 외부 자료 | 시안·기획 문서 링크 | 없으면 `해당 없음` |
| 용어 | 이 기능에서 새로 만든 말이나 팀원이 다르게 이해할 수 있는 말의 풀이 | 앱·도메인에서 일반적으로 쓰는 말은 쓰지 않는다. 처음에는 `해당 없음`으로 두고 리뷰에서 질문이 나오면 추가한다. 한 번만 쓰는 말은 그 문장 안에서 푼다 |
| 사용자 흐름 | 사용자 시나리오. 사용자가 무엇을 하면 무엇이 보이는지를 계기(진입·조작·새로고침·실패)별로 이어지는 이야기로 | 시스템 내부 동작(호출·저장)은 쓰지 않는다 |
| 정책 규칙 | `P번호. 규칙`. 정상 흐름에서 정해진 결정 | 결정 하나를 한 문장으로 쓴다. 이유·세부 설명을 붙이지 않는다. 어떻게 만드는지는 쓰지 않는다. 정상이 아닌 경우는 `예외 처리`에 쓴다. 다섯 개를 넘으면 주제별 소제목(`###`)으로 묶고 번호는 이어 간다 |
| 예외 처리 | `번호 \| 상황 \| 사용자에게 보이는 것` 표. 번호는 E. 실패·빈 결과·정보 없음·권한·네트워크 끊김·무반응 조작 등 정상 흐름이 아닌 모든 경우 | 이 절이 예외의 정본이다. 무엇이 보이고 숨는지, 무엇이 일어나는지만 쓴다. 모양과 고정 문구는 시안 노드를 가리킨다. 기존 앱 기능(오류 알림 등)이 처리하면 그 기능 이름과 이 경우의 결과를 쓴다 |
| 보여 줄 정보 | `보여 줄 것 \| 내용과 형식 \| 보이는 조건 \| 필요한 정보` 표 | 내용과 형식에는 값에 따라 바뀌는 표기 규칙만 쓴다(날짜 형식, 단위, 범위 표기 등). 필요한 정보에는 그 항목을 보이려면 어디서 무엇을 받아야 하는지 쓴다. 배치·모양·고정 문구는 쓰지 않는다. 화면이 없으면 `해당 없음` |
| 입력과 연동 | `구분 \| 항목 \| 값과 형식 \| 비고` 표. 구분은 `입력`(사용자가 넣거나 고르는 것)과 `연동`(정보를 받아 오는 외부 서비스·서버) | 값의 범위·형식·기본값까지 쓴다. 연동은 어디서 무엇을 받는지만 쓰고 호출 방식은 쓰지 않는다 |
| 쓰는 기존 앱 기능 | `기존 기능 \| 이 기능에서의 쓰임` 표. 이 기능이 가져다 쓰는 기존 앱 기능 | 동작을 다시 쓰지 않고 쓰이는 곳(P·E 번호)만 쓴다. 기존 기능의 동작을 바꿔야 하면 그 기능의 문서를 고치거나 `목표`에 변경으로 적는다 |
| 수용 조건 | `번호 \| 상황 \| 결과 \| 근거` 표. 번호는 A, 근거는 P·E번호 | `검증 항목의 세 단계` 참조. 정하지 못한 행은 결과 칸에 `미확정`과 추천값. 해당하는 장면이 없으면 `해당 없음` |
| 기존 동작 보존 | 이 변경 후에도 바뀌면 안 되는 사용자 동작 | 신규 기능이라 보존할 동작이 없으면 `해당 없음` |
| 미결 사항 | 정책 수준에서 지금 정할 수 없는 것 | |
| 변경 이력 | 진행 승인 후 개정마다 `날짜 — 바뀐 것 — 발견 단계 — 이유` 한 줄. 발견 단계는 `spec 검토`·`design 작성`·`plan 작성`·`구현`·`리뷰`·`테스트` 중 하나 | 첫 작성이면 `해당 없음`. 구현 중 문서가 몇 번, 왜 바뀌었는지 이 이력으로 확인한다 |

## design.md

| 절 | 내용 | 판정 기준 |
|---|---|---|
| 작성일 | `YYYY-MM-DD` | 제목 바로 아래 |
| 외부 자료 | API 문서·원본 데이터 출처 링크 | 없으면 `해당 없음` |
| 사용 계약 | 조상 문서의 `공유 계약` 중 이 단위가 쓰는 항목과, 만드는 쪽인지 쓰는 쪽인지 | 나누지 않은 기능이면 `해당 없음` |
| 용어 | 이 기능에서 새로 만든 말이나 개발자가 다르게 이해할 수 있는 기술 용어의 풀이 | 개발자라면 아는 일반 기술 용어는 쓰지 않는다. 처음에는 `해당 없음`으로 두고 리뷰에서 질문이 나오면 추가한다 |
| 처리 흐름 | 계기별로 무엇을 어떤 순서로 부르고 저장하는지, 취소·실패 처리 | `spec`의 사용자 흐름 단계와 대응되게 쓴다 |
| 데이터 모델 | 만들고 쓰는 값의 타입·필드·의미·null 가능성 | 플랫폼 중립 표기(정수·문자열·날짜·열거형·목록·맵) |
| 외부 연동 | API마다 메서드·경로, 파라미터와 값의 출처·생략 규칙, 응답 필드와 형식·쓰임, 오류 판정, 인증. 하위 절 `앱 기존 구성요소`에 이 기능이 쓰는 기존 화면·전역 상태·공통 처리를 `구성요소 \| 넘기는 값 \| 기대하는 결과` 표로 | 연동이 없으면 `해당 없음` |

| 고려한 대안 | 검토했으나 버린 기술 안과 이유, 리뷰 발견 중 반영하지 않은 것 | 정책 수준의 대안은 `spec`의 배경에 적는다 |
| 미결 사항 | 설계 수준에서 지금 정할 수 없는 것 | |
| 변경 이력 | 진행 승인 후 개정마다 `날짜 — 바뀐 것 — 발견 단계 — 이유` 한 줄. 발견 단계는 `spec 검토`·`design 작성`·`plan 작성`·`구현`·`리뷰`·`테스트` 중 하나 | 첫 작성이면 `해당 없음`. 구현 중 문서가 몇 번, 왜 바뀌었는지 이 이력으로 확인한다 |

`design` 본문(플랫폼 종속 사항 밖)에는 이 리포의 파일 경로·모듈·클래스·함수 이름, 플랫폼·프레임워크 용어(UI 프레임워크·상태 관리 계층의 이름, 프로젝트 사실 `계약`에 나오는 용어)를 쓰지 않는다. 외부 정본(API 문서 등)은 스키마 전체 대신 이 기능이 쓰는 필드와 의미를 적는다.

## plan.md

| 절 | 내용 | 판정 기준 |
|---|---|---|
| 적용 규칙 | 프로젝트 사실의 문서 항목(`코드 스타일`·`아키텍처`·`테스트 문서`) 중 관련 문서와 절, 그 절이 이 작업에 요구하는 것 | 구현 단계가 이 목록을 읽는다. 파일을 새로 만들거나 나누면 `코드 스타일` 문서의 파일 배치 기준을 포함한다. 관련 문서가 없으면 `해당 없음` |
| 구조 결정 | 모듈·패키지·파일 배치와 각 배치의 근거 | 근거는 `적용 규칙`의 절이나 열어 본 선례 파일이다 |
| 구현 계약 | 추가·변경되는 계약만 before/after — 프로젝트 사실 `계약`의 종류별로: 외부 인터페이스(엔드포인트·스키마)와 새로 쓰는 필드의 귀착지 / 공개 모델 필드 / 진입점·인자·복귀 경로 / 공용 시그니처 | 각 공개 모델 필드에 출처와 초기값을 적는다. `design` 처리 흐름의 실패 처리가 어떤 계약상의 결과가 되는지 적는다 |
| 화면 구성 | 요소별 재사용·확장·신규 판정과 근거 | 대상 파일을 열어 시그니처를 확인한 뒤 적는다. UI 변경이 없으면 `해당 없음` |
| 테스트 케이스 | 첫 줄에 `TDD: 적용 \| 미적용 — 근거`. 이어서 `[태그] 테스트명(프로젝트 테스트 문서의 함수명 형식) — 입력 — 기대 결과`, 단위 테스트로 안 되면 `[태그] 수동 확인: <절차>` 또는 `[태그] 리뷰 확인: <항목>` | `검증 항목의 세 단계` 참조. TDD 적용이면 ④가, 미적용이면 ⑥이 test-engineer에 목록을 그대로 넘긴다. 수동 확인은 ⑥ 완료 보고에, 리뷰 확인은 ⑤ 위임 메시지에 옮긴다 |
| 작업 순서 | 독립적으로 검증 가능한 단계마다 할 일, 파일 표(경로 / 신규·수정 / 할 일), 검증 명령, 커밋 경계 | 앞 단계가 만들지 않은 것을 뒤 단계가 쓰지 않는다 |
| 회귀 대상 | 공용 파일을 고칠 때 함께 확인할 기존 호출부 | 인터페이스를 늘리면 구현체와 테스트 대역(fake·stub)을 grep으로 확인해 있는 것만 적는다 |
| 고려한 대안 | 리포 수준에서 버린 안(구조·라이브러리·배치)과 이유 | |

## 작성 순서와 반려

1. `spec.md`를 쓰고 자기 대조 후 제시해 진행 승인을 받는다. 트리면 위에서 아래로.
2. `design.md`를 쓰고 자기 대조 후 제시한다. 처음 제시할 때 `이식성 시험`을 한 번 수행해 결과를 함께 내고, 부분 분할 여부를 사용자에게 묻는다. 진행 승인을 받는다.
3. `plan.md`를 쓰고 자기 대조 후 제시해 진행 승인을 받는다.
4. 구현하면서 확정된 것과 바뀐 것을 해당 문서에 반영해, 기능을 마칠 때 세 문서가 최종 모습이 되게 한다.

- **진행 승인**은 문서가 완성됐다는 판정이 아니라 "다음 단계로 진행해도 된다"는 판정이다. `[차단]` 미결만 진행을 막고, `[비차단]` 미결과 아직 정하지 못한 것은 남긴 채 진행한다.
- 앞 문서의 진행 승인 전에 뒤 문서를 쓰지 않는다. 각 문서를 쓰기 전에 필요한 탐색을 한다 — `spec`은 기존 동작, `design`은 외부 스펙과 기존 로직, `plan`은 코드베이스.
- `[차단]` 미결이 남아 있으면 진행 승인을 요청하지 않고 그 결정부터 받는다.
- **보완 흐름(정상 경로)**: `design`을 쓰다가 정책 결정이 빠진 것을 발견하면 그 항목을 `[차단]` 질문으로 올리고, 답을 받아 `spec`을 고쳐 다시 승인받은 뒤 이어 쓴다. `plan`을 쓰다가 설계가 빠진 것을 발견하면 같은 방식으로 `design`을 고친다. 다음 문서에서 앞 문서의 결정을 대신 정하지 않는다.
- 앞 문서가 바뀌면 그 문서를 근거로 쓴 뒤 문서를 다시 승인받는다.

## 이식성 시험

`spec.md`와 `design.md`만으로 다른 플랫폼의 `plan`을 쓸 수 있는지 서브에이전트로 확인한다. `세 문서는 차례로 이어져야 한다`를 기계적으로 확인하는 단계다. 자동 수행은 `작성 순서와 반려` 2단계의 한 번뿐이고, 다시 돌리기는 사용자가 요청할 때만 한다.

1. `general-purpose` 서브에이전트에 `model: sonnet`으로 새로 위임한다.
2. 읽는 범위는 그 기능의 `spec.md`와 `design.md`(나눴으면 부분 파일과 `사용 계약` 항목 포함)다. `spec.md`를 먼저 끝까지 읽게 한다.
3. 위임 메시지에는 경로와 다음 지시만 담는다 — "지정한 범위만 읽고 <이 리포와 다른 플랫폼> 구현 계획을 세워라. 리포의 다른 파일은 읽지 마라. 문서에 없는 정보는 추측으로 채우지 말고 `질문`에 적고, 질문마다 `동작 정보 누락`·`미정의 참조`·`플랫폼 결정`으로 분류하라. 문서 사이의 어긋남은 양쪽 문장을 인용해 따로 적어라. 보고에 읽은 파일 목록을 포함하라."
4. 지정 범위 밖의 파일을 읽었으면 그 시험은 무효다.
5. 판정: 어긋남, `동작 정보 누락`, `미정의 참조`는 문서 결함이다. `플랫폼 결정`은 정상이다.
6. 통과 기준: 어긋남이 0건이다. 나머지 결함(`동작 정보 누락`·`미정의 참조`)은 지금 정할 수 있으면 고치고, 정할 수 없으면 `미결 사항`에 `[차단]`·`[비차단]`으로 기록한다. 모든 결함을 없애야 통과하는 것은 아니다.
7. 고친 것과 미결로 기록한 것을 함께 제시한다. 다시 시험할지는 사용자에게 맡기고, 다시 할 때는 새 서브에이전트로 한다.

## 자기 대조

각 문서를 쓴 직후, 사용자에게 제시하기 전에 작성자가 수행한다. 계획에 대한 유일한 사전 검증이므로 생략하지 않는다. 목적은 완결 판정이 아니라 두 가지다 — 쓴 내용이 정확한가, 알고 있는 빈 곳이 `미결 사항`에 드러나 있는가. 미결이 남아 있는 것은 정상이다.

**구현에서 실제로 문제를 일으키거나 그 문서의 독자가 읽고 판단하지 못할 것만 지적으로 본다.** 정보가 빠졌거나, 서로 모순되거나, 해석이 갈려 다른 것을 만들게 될 문장, 그리고 공통 작성 선을 어긴 줄이 지적이다. 지적은 제시 전에 고친다. 고칠 수 없는 것(사용자 답이 필요한 것)만 제시에 함께 낸다.

**spec 항목**

- `정책 규칙`·`목표가 아닌 것`의 각 줄이 결정된 것인가. 현재 동작을 결정처럼 쓴 곳은 없는가.
- 풀이가 필요한 말은 처음 나오는 문장 안이나 `용어`에서 풀었는가. 일반적으로 아는 말을 풀이한 곳은 없는가. (design에도 같은 기준을 적용한다)
- `design`을 쓸 때 필요한 제품·운영 결정(사용자에게 보이는 값·문구·경계·실패 시 결과, 새 데이터를 받는 시점, 기록할 것)이 정해져 있는가. 정할 수 없는 것은 `[차단]`으로 드러나 있는가.
- 구현 방법(호출 방식·저장·계산 방법·이벤트 이름·파라미터)을 쓴 곳이 없는가.
- `요약` 첫 줄이 기능을 한 문장으로 정의하는가.
- 시안에서 확인되는 배치·모양·고정 문구를 글로 다시 쓴 곳이 없는가.
- `보여 줄 정보`의 각 항목에 보이는 조건과 필요한 정보가 있는가. `입력과 연동`의 각 항목에 값의 범위·형식이 있는가. `예외 처리`가 정상 흐름이 아닌 모든 경우를 덮고, 각 경우에 보이는 것이 정해져 있는가.
- A가 P·E 문장을 다시 쓰지 않는가. 경계값·조합·순서와 시간·시안에 없는 동작 중 리뷰어가 놓칠 장면이 A에 있는가. 사용자가 확인할 수 없는 P는 `design`의 V로 넘긴다고 표시돼 있는가.
- 정책 규칙이 결정 하나씩 한 문장인가. 다섯 개를 넘으면 주제별로 묶였는가.
- 같은 규칙·문구가 정본 밖에서 다시 쓰이지 않았는가(`spec.md`의 한 내용은 한 곳에만).
- 사용자 흐름·정책 규칙에 시스템 내부 동작(호출·저장·계산 방법)이 들어가지 않았는가.
- 앱에 이미 있는 기능의 동작을 이 기능의 정의처럼 다시 쓴 곳이 없는가.
- `미결 사항`에 문서·코드로 정해지는 내용이 없고, 항목마다 `[차단]`·`[비차단]`이 붙어 있는가.

**design 항목**

- `spec`에 있어야 할 결정을 이 문서가 대신 정한 곳이 없는가. 있으면 `[차단]`으로 올려 `spec`을 고친다.
- `plan`을 쓸 때 남는 것이 리포 안의 배치·이름 같은 플랫폼 결정뿐인가.
- 모든 P가 설계 규칙·처리 흐름에서 구현되는가. `spec`의 결과를 다시 쓴 곳이 없는가.
- V가 A를 다시 쓰지 않고, 설계 규칙의 분기·경계와 사용자가 확인할 수 없는 P를 덮는가.
- 본문이 플랫폼 중립인가(`## 검증`의 명령).
- `처리 흐름`·`외부 연동`·`설계 규칙`에 값·순서·경계가 빠져 해석이 갈리는 문장이 없는가.
- 나눴으면: `사용 계약`과 어긋나지 않는가, 형제 참조가 없는가, 계약에 만드는 쪽 내부 조건이 없는가.
- 민감 정보 원문이 사용자 확인 없이 들어가지 않았는가. 본문에 외부 링크가 따로 달려 있지 않은가.

**plan 항목**

- `design`에 있어야 할 결정을 이 문서가 대신 정한 곳이 없는가.
- 구현하는 사람이 새로 결정할 것 없이 `작업 순서`대로 따라갈 수 있는가.
- 모든 A와 V가 테스트 케이스나 확인 줄로 이어지는가.
- `구조 결정`의 배치마다 근거가 있는가.
- `작업 순서`의 파일 표가 `구조 결정`·`구현 계약`을 전부 덮고, 단계 간 의존 역전이 없는가.
- `spec`·`design`의 내용을 다시 적은 곳이 없는가.
- `회귀 대상`·파일 표의 각 행이 열어 본 것인가. 확인하지 못한 행은 `미확인`으로 적고 미해결로 낸다.

### 결과 보고

자기 대조를 마치면 결과를 문서 끝의 `---` 아래에 적는다.

```
자기 대조(spec|design|plan): 통과 | 미해결 있음
- 고침: [절 이름], [절 이름]
- 미해결 [절 이름]: 무엇이 비었는지 — 어떤 문제가 되는지 / 사용자에게 무엇이 필요한지
```

고친 항목은 절 이름만 적는다. 문서를 제시할 때 응답에는 미해결 항목만 옮긴다.

## 검증

- 자기 대조 수행: 각 문서 끝에 결과 블록이 있는지 확인한다.
- 플랫폼 중립: `sed '/^## 플랫폼 종속 사항/,$d' design.md | grep -nE '<리포 소스 확장자>|<모듈 디렉터리>/|<프레임워크·계약 용어>'`가 아무것도 출력하지 않는지 확인한다. 패턴은 리포의 소스 확장자, 최상위 모듈 디렉터리 이름, 프로젝트 사실 `계약`의 용어로 채운다.
- 구현 용어: `grep -nE 'API|캐시|파라미터|응답|엔드포인트' spec.md`의 각 줄이 `외부 자료` 표 안이거나 사용자가 보는 문구인지 확인한다.
- 추적: `spec`의 P·E·A 번호, `design`의 V 번호를 모아 `design`·`plan`에서 각각 한 번 이상 나오는지 grep으로 확인한다. 사용자가 확인할 수 있는 P·E는 `plan` 테스트 케이스에 태그로 나오고, 확인할 수 없는 P는 그 P를 표시한 V가 있는지 확인한다.
- 외부 링크: `외부 자료` 절 밖에 `http`가 없는지 확인한다.
- 가독성: `spec`의 `요약`·`사용자 흐름`, `design`의 `처리 흐름`을 해당 독자 기준으로 읽어 풀이 없는 용어나 기호 나열로 압축한 줄이 없는지 확인한다. 실패 사례: 2026-09-29 스펙 초안이 심볼·약칭 압축과 절 간 반복으로 읽히지 않았다.
- 실재성: `plan`이 지목한 파일·컴포넌트·엔드포인트가 리포와 스펙에 실제로 존재하는지 확인한다.
- 절 이름: 각 문서의 `##` 제목 집합이 템플릿과 같은지 확인한다.
- 이식성 시험 수행: `design` 첫 제시에 이식성 시험 결과(어긋남 수, 질문 분류별 수, 통과 여부)가 있는지 확인한다. 실패 사례: 2026-10-07 기능 트리 시험에서 상위 계약이 하위 문서 세부를 요약해 어긋남 4건이 생겼다.
