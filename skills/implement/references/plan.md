# 계획 파일 작성법

목적: 복합 수준 작업의 계획을 이 문서만 읽고 구현에 착수할 수 있는 계획 파일로 남긴다. 경계 내·표준 수준은 계획 파일을 만들지 않는다 — `SKILL.md`의 ② 계획 참조.

`docs/specs/<topic>-design.md`에 쓴다. `<topic>`은 작업 대상을 나타내는 소문자 케밥 케이스다. 작업 완료 후에도 삭제하지 않고 코드와 함께 커밋한다.

## 작성 선

이 파일의 독자는 셋이다 — 방향을 승인하는 사용자, 판정 근거로 쓰는 code-reviewer·test-engineer, 나중에 "왜 이렇게 만들었는가"를 확인하는 사람. **깊이는 이 독자들이 읽고 제안할 수 있는 수준으로 정한다.** 판단·계약·근거는 적고, 코드를 옮겨 적지 않는다.

- **바뀌는 것만 쓴다.** 계약은 추가·변경되는 항목을 before/after로 적는다. 그대로인 필드·컴포넌트·경로는 나열하지 않는다.
- **전사 금지.** 응답 스펙 전문, 컴포넌트 트리, 카피 원문, 시안 노드 id 목록, reduce 로직, 리터럴 인자를 채운 호출 코드는 적지 않는다. 필요하면 링크·경로 하나로 가리킨다.
- **설계 절에는 수단을 적지 않는다.** 헬퍼·연산자·저장 키·의존성 좌표·파일 경로·DI 배치는 실행 절의 파일별 작업에 적는다. 설계에 남는 것은 동작·조건·실패 시 결과, 계약의 이름과 모양(입력 이벤트·부수 효과·시그니처·모델 필드·초기값), 판정 규칙, 버린 안이다.
- **열어 본 것만 적는다.** 파일 경로·심볼·재사용 판정은 그 파일을 열어 확인한 뒤 적는다. 조사 요약의 "재사용 가능"은 계약이 아니다. 확인하지 못했으면 `미확인`으로 적는다.
- **도메인 타입은 리포에서 먼저 찾는다.** 표준 라이브러리 타입을 쓰기 전에 프로젝트의 도메인 모델에 대응 타입이 있는지 확인한다.
- 각 절은 지우지 않는다. 해당 없으면 `해당 없음` — 빈칸은 누락과 구분되지 않는다.
- 절 이름은 템플릿 그대로 쓴다. code-reviewer·test-engineer·⑥ 위임이 절 이름으로 내용을 찾는다. 계약 종류가 많으면 `계약 변경` 안에서 하위 제목으로 나눈다 — 절 자체를 쪼개거나 이름을 바꾸지 않는다.
- 분량 상한은 설계 절 7KB, 실행 절 4KB다. 각 제시 시점에 `wc -c`로 재어 결과 보고에 실측값을 적는다. 상한은 제시 시점 측정값에만 적용한다 — ⑤·⑦에서 `이외 고려 사항`에 붙는 항목은 재측정하지 않는다(상한의 목적은 승인자가 읽을 분량 제한이다). 넘으면 전사가 섞인 것이다 — 실측값이 남으므로 상한을 올릴지 전사를 뺄지는 그 값으로 판단한다. 상한을 올리는 근거는 특정 스펙이 넘친 것이 아니라 규칙이 늘어 모든 스펙의 분량이 구조적으로 는 것이어야 한다.

## 절 정의

구조는 테크스펙(요약·배경·목표·비목표·계획·이외 고려 사항·마일스톤)을 따른다. **설계**(요약~이외 고려 사항)는 사용자 승인 대상이고, **실행**(마일스톤)은 승인된 설계에서 도출된다. 설계는 승인 전에 쓰고 실행은 승인 후 같은 파일에 이어 쓴다(`SKILL.md` ②). 접근이 반려되면 설계부터, 내용이 반려되면 실행만 고친다.

### 설계 절

| 절 | 내용 | 판정 기준 |
|---|---|---|
| 작성일 | `YYYY-MM-DD` | 제목 바로 아래. 언제 시점의 판단인지 드러나야 한다 |
| 요약 | 무엇을 왜 만드는지 3줄 | 재개·검토 시 첫 진입점 |
| 확정 사항 | 사용자가 정해야 했던 선택과 확정값을 한 줄씩. 형식: `항목 — 확정값 (대안: X, 버린 이유 한 줄)` | 승인자가 가장 먼저 읽는 자리다. 본문에 사용자 결정을 흩뿌리지 않고 여기로 모은다. 아직 확정되지 않은 항목은 `미확정`으로 적어 승인 요청에 포함한다. 8줄을 넘으면 요청이 과도하게 큰 것이므로 분할을 제안한다. 대안·이유의 상세는 `이외 고려 사항`에 두고 여기서는 한 줄과 포인터만 |
| 배경 | 이 요구가 나온 맥락, 이전 시도가 있으면 그 결과. 방향 합의를 생략했으면 대안이 하나뿐인 근거 | 구현 중 분기 판단에 쓰이는 것만. 없으면 `해당 없음` |
| 수용 조건 | 완료를 판정하는 검증 가능한 문장 목록 | 성공만 적지 않는다. 대상에 해당하는 실패 경로(네트워크 에러·빈 응답·비로그인·권한 없음)를 조건으로 함께 적는다 |
| 테스트 케이스 | 수용 조건마다 `테스트명(프로젝트 테스트 문서의 함수명 형식) — 입력 — 기대 결과` 한 줄. 단위 테스트로 검증할 수 없는 조건은 둘로 나눈다 — 실행해야 보이는 동작(외부 SDK·기기 상태)은 `수동 확인: <확인 절차>`, 코드를 읽으면 판정되는 구조(분기 유무·호출 순서)는 `리뷰 확인: <항목>` 한 줄 | ⑥이 test-engineer에 그대로 넘기고, 수동 확인 줄은 ⑥ 완료 보고에, 리뷰 확인 줄은 ⑤ 위임 메시지에 옮긴다. 검증 방법이 없으면 수용 조건이 아니라 `이외 고려 사항`이다. 단위 테스트 대상 코드 변경이 없으면 `해당 없음` |
| 비목표 | 이번에 하지 않는 것 | 이번 변경에 필요 없는 인접 정리·리팩터링은 여기 적어 배제한다. 손대는 코드 자체의 결함이 작업을 막으면 배제하지 말고 파일별 작업에 넣는다 |
| 계약 변경 | 추가·변경되는 계약만 before/after — 엔드포인트와 새로 쓰는 응답 필드의 귀착지 / 상태 필드·입력 이벤트·부수 효과 / 화면 진입점·인자·진입·복귀 경로 / 공용 시그니처 | 그대로인 항목은 적지 않는다. 호출 실패 시 어떤 상태·효과가 되는지는 적는다 |
| 화면 구성 | 요소별 재사용·확장·신규 판정과 근거, 시안 링크 하나 | 재사용 판정은 대상 파일을 열어 시그니처를 확인한 뒤 적는다. 트리·카피·노드 id는 적지 않는다. 화면에 실제로 있는 상태(로딩·빈·에러·비로그인·권한)만 적고, 없는 상태는 `해당 없음` |
| 이외 고려 사항 | 검토했으나 버린 안과 이유, 리뷰 발견 중 반영하지 않은 것과 이유 | 채팅 방향 합의에서 버린 접근을 포함한다. 검토자가 "왜 이걸 안 했나"를 보는 자리다 |

### 실행 절

| 절 | 내용 | 판정 기준 |
|---|---|---|
| 파일별 작업 | 경로 / 신규·수정 / 할 일 한 줄 | 모듈 경계를 넘는 파일이 빠지지 않았는지 확인한다 |
| 구현 순서 | 독립적으로 검증 가능한 단위, 단위별 검증 명령과 커밋 경계 | 심볼 표는 적지 않는다. 앞 단위가 만들지 않은 것을 뒤 단위가 쓰면 계약 변경 절이 빠진 것이다 |
| 회귀 대상 | 공용 파일을 고칠 때 함께 확인할 기존 호출부 | 공용 컴포넌트·모델·네비게이션 규약을 건드리면 반드시 적는다. 인터페이스를 늘리면 구현체와 테스트 대역(fake·stub)을 grep으로 확인해 있는 것만 적는다 — 추정으로 행을 만들지 않는다 |
| 참조 문서 | 프로젝트 사실 `문서 인덱스`로 특정한 문서와 절 | 구현 단계가 이 목록을 읽는다 |

## 템플릿

```markdown
# <작업명>

**작성일**: YYYY-MM-DD

## 설계
### 요약
### 확정 사항
### 배경
### 수용 조건
- [ ]
### 테스트 케이스
### 비목표
### 계약 변경
### 화면 구성
### 이외 고려 사항

---
자기 대조(설계): …

## 실행
### 파일별 작업
| 경로 | 신규/수정 | 할 일 |
|---|---|---|
### 구현 순서
### 회귀 대상
| 고치는 것 | 확인할 기존 화면 |
|---|---|
### 참조 문서

---
자기 대조(실행): …
```

## 자기 대조

계획을 쓴 직후, 사용자에게 제시하기 전에 작성자가 수행한다. 계획에 대한 유일한 사전 검증이므로 생략하지 않는다.

**구현 단계에서 실제로 문제를 일으킬 것만 지적으로 본다.** 계약이 빠졌거나, 서로 모순되거나, 해석이 갈려 다른 것을 만들게 될 문장 — 이것이 지적이다. 문구 다듬기, 절마다 상세도가 다른 것, 취향 차이는 지적이 아니다. 이런 항목은 고치지도 보고하지도 않는다.

지적은 제시 전에 고친다. 고칠 수 없는 것(사용자 답이 필요한 것)만 제시에 함께 낸다.

**설계 항목** — 설계 절을 쓴 뒤 제시 전에 대조한다.

- 수용 조건마다 그것을 일으키는 입력과 결과로 나는 상태·효과가 계약 변경 절에 있고, 실패 경로 조건이 있는가.
- 수용 조건마다 테스트 케이스 또는 `수동 확인`·`리뷰 확인` 줄이 있는가 — 실패 경로 포함. 케이스는 `테스트명 — 입력 — 기대` 형식으로 한 줄씩인가(여러 케이스를 한 줄에 압축하면 ⑥이 그대로 구현할 수 없다). 셋 다 없는 조건은 검증 불가이므로 `이외 고려 사항`으로 옮긴다.
- 계약 변경 절의 각 상태 필드에 출처(응답 필드 또는 화면 요소)와 초기값이 적혀 있는가.
- 본문에 흩어진 사용자 결정이 `확정 사항`에 전부 모여 있는가. 미확정 항목이 `미확정`으로 표시돼 있는가.
- `TBD`·"적절히 처리"·"테스트 작성" 같은 미룸이 남았는가 — 실제 내용으로 바꾸거나 지금 정할 수 없는 이유를 적는다.
- 전사(트리·카피·전체 필드 나열)나 수단(헬퍼·키·경로·의존성)이 섞여 설계 절이 7KB를 넘지 않는가.

**실행 항목** — 실행 절을 쓴 뒤 제시 전에 대조한다.

- 파일별 작업이 계약 변경을 전부 덮는가.
- 구현 순서에 의존 역전이 없는가 — 앞 단위가 만들지 않은 것을 뒤 단위가 쓰지 않는가.
- 파일별 작업에 리터럴 코드가 있는가 — 설계에 문장으로 있는 것을 코드로 다시 쓴 것 포함. 함정 경고(왜 그렇게 해야 하는지)는 코드가 아니므로 남긴다.
- 회귀 대상·파일별 작업의 각 행이 설계 단계에서 열어 본 것인가. 확인하지 못한 행은 `미확인`으로 적고 미해결로 낸다 — 실행 단계에서 새로 탐색하지 않는다.
- 실행 절이 4KB를 넘지 않는가.

### 결과 보고

각 단계의 자기 대조를 마치면 결과를 해당 절 끝의 `---` 아래에 적는다(템플릿 위치). 설계 블록은 설계 제시 시, 실행 블록은 실행 제시 시 추가한다.

```
자기 대조(설계|실행): 통과 | 미해결 있음 (대조 N/N)
- 분량: <wc -c 실측값> / <상한>
- 고침: [절 이름], [절 이름]
- 미해결 [절 이름]: 무엇이 비었는지 — 구현 단계에 어떤 문제가 되는지 / 사용자에게 무엇이 필요한지
```

`N/N`은 대조한 항목 수와 해당 단계 목록의 전체 항목 수다 — 분모에 못 미치면 대조를 마치지 않은 것이다. 분량은 아래 명령으로 잰다.

```bash
sed -n '/^## 설계/,/^---$/p' docs/specs/<topic>-design.md | wc -c   # 설계 — 블록 제외
sed -n '/^## 실행/,/^---$/p' docs/specs/<topic>-design.md | wc -c   # 실행 — 블록 제외
```

고친 항목은 절 이름만 적고 내용은 적지 않는다. 계획을 제시할 때 응답에는 미해결 항목만 옮긴다 — 미해결이 없으면 자기 대조를 응답에 내지 않는다.

## 검증

- 자기 대조 수행: 계획 파일에 설계·실행 블록이 각각 있고 `N/N` 분모가 해당 단계 체크리스트 항목 수(설계 6, 실행 5)와 일치하는지 확인한다.
- 자족성: 이 계획 파일과 요청 원문만으로 구현 착수가 가능한지 — 포인터만 있고 내용이 없는 절이 남았는지 확인한다.
- 미룸: "구현 시 확인·구현 시 결정"으로 남긴 항목이 지금 결정할 수 없는 것인지 확인한다. 문서를 읽거나 코드를 보면 정해지는 것을 미뤘으면 계획 단계에서 정한다.
- 자기 정합: 요약·배경이 비목표·확정 전제와 어긋나지 않는지 확인한다. 범위에서 뺀 것은 비목표에만 적지 말고 요약·배경에서도 드러나야 한다.
- 실재성: 계획이 지목한 파일·컴포넌트·엔드포인트가 리포와 스펙에 실제로 존재하는지 확인한다.
- 분량: 결과 보고의 실측값이 위 명령의 출력과 같고 상한(설계 7KB·실행 4KB) 이하인지 확인한다. 넘으면 설계는 계약 변경·화면 구성 절의 전사·수단을, 실행은 파일별 작업의 리터럴 코드를 찾아 뺀다.
- 절 이름: 계획 파일의 `###` 제목 집합이 템플릿과 같은지 확인한다.
