# 계획 파일 작성법

목적: 복합 수준 작업의 계획을 이 문서만 읽고 구현에 착수할 수 있는 계획 파일로 남긴다. 경계 내·표준 수준은 계획 파일을 만들지 않는다 — `SKILL.md`의 ② 계획 참조.

프로젝트 사실 `스펙 위치` 디렉토리에 `<topic>-design.md`로 쓴다. 항목이 없으면 위치를 묻는다. `<topic>`은 작업 대상을 나타내는 소문자 케밥 케이스다. 작업 완료 후에도 삭제하지 않고 코드와 함께 커밋한다.

## 작성 선

**이 문서는 사람이 읽는다. 가독성이 다른 모든 작성 규칙보다 우선한다.** 에이전트는 절 이름으로 필요한 내용을 찾을 뿐이므로, 에이전트를 위해 사람의 가독성을 희생하지 않는다. 아래 규칙이 가독성과 부딪치면 가독성을 따른다.

독자는 플랫폼·언어는 알지만 이 프로젝트는 모르는 개발자다. 이 독자가 `한눈에 보기`와 `동작 원리`만 읽고 변경을 설명할 수 있어야 한다.

- 완결된 문장으로 쓴다. `A·B → C / D` 같은 기호 나열이나 약칭으로 압축하지 않는다.
- 한 줄에는 정보 하나만 담는다. 조건·결과·이유를 한 줄에 몰아넣지 않는다.
- 코드 심볼과 프로젝트 고유 용어는 처음 나올 때 역할을 풀어 쓴다. 심볼만 나열하지 않는다.
- 표는 여러 항목을 같은 축으로 비교할 때만 쓴다. 설명을 표 셀에 욱여넣지 않는다.
- 예시는 추상 이름(Feature A 등)이 아니라 실제 화면·기능 이름으로 든다.
- **한 규칙은 한 절에만 쓴다.** 다른 절에서 필요하면 절 이름으로 가리킨다. 같은 결정이 여러 절에 반복되면 어느 쪽이 정본인지 알 수 없다.
- **바뀌는 것만 쓴다.** 계약은 추가·변경되는 항목을 before/after로 적는다. 그대로인 필드·컴포넌트·경로는 나열하지 않는다.
- **전사하지 않는다.** 응답 스펙 전문, 컴포넌트 트리, 카피 원문, 시안 노드 id 목록, reduce 로직은 적지 않는다. 필요하면 링크·경로 하나로 가리킨다. 동작을 이해하는 데 필요한 시그니처·모델 정의는 코드 블록으로 보여 준다.
- **파일 경로는 실행 절에만 쓴다.** 설계 절의 범위는 모듈·기능 단위로 적는다.
- **열어 본 것만 적는다.** 파일 경로·심볼·재사용 판정은 그 파일을 열어 확인한 뒤 적는다. 확인하지 못했으면 `미확인`으로 적는다.
- **도메인 타입은 리포에서 먼저 찾는다.** 표준 라이브러리 타입을 쓰기 전에 프로젝트의 도메인 모델에 대응 타입이 있는지 확인한다.
- 각 절은 지우지 않는다. 해당 없으면 `해당 없음` — 빈칸은 누락과 구분되지 않는다.
- 절 이름은 템플릿 그대로 쓴다. code-reviewer·test-engineer·⑥ 위임이 절 이름으로 내용을 찾는다.

## 절 정의

절 순서는 독자가 이해하는 순서다 — 무엇인가 → 어떻게 동작하나 → 규칙은 무엇인가 → 왜 바꾸나 → 코드는 무엇이 바뀌나 → 무엇이 보존되나 → 어떻게 검증하나 → 무엇을 버렸나. **설계**(한눈에 보기~고려한 대안)는 사용자 승인 대상이고, **실행**(작업 순서~참조 문서)은 승인된 설계에서 도출된다. 설계는 승인 전에 쓰고 실행은 승인 후 같은 파일에 이어 쓴다(`SKILL.md` ②). 접근이 반려되면 설계부터, 내용이 반려되면 실행만 고친다.

### 설계 절

| 절 | 내용 | 판정 기준 |
|---|---|---|
| 작성일 | `YYYY-MM-DD` | 제목 바로 아래. 언제 시점의 판단인지 드러나야 한다 |
| 한눈에 보기 | 목적 한 문장, 변경 전, 변경 후, 핵심 규칙(5개 안팎) | 이 절만 읽고 30초 안에 변경을 설명할 수 있어야 한다. 규칙의 상세는 `수용 조건`에 두고 여기서는 한 줄씩만 |
| 동작 원리 | 대표 흐름 하나와 예외 흐름 하나를 실제 화면·호출 이름으로 그린 흐름도 | 뒤 절의 계약을 읽기 전에 동작을 머릿속에 그릴 수 있어야 한다. 흐름이 없는 작업(순수 UI 교체 등)은 `해당 없음` |
| 수용 조건 | `상황 | 결과` 표. 사용자가 정한 규칙과 실패 경로가 모두 여기 모인다 | 완료를 판정하는 검증 가능한 행이어야 한다. 성공만 적지 않고 해당하는 실패 경로(외부 호출 실패·빈 결과·잘못된 입력·권한 없음)를 행으로 넣는다. 아직 정하지 못한 규칙은 결과 칸에 `미확정`과 추천값을 적어 승인 요청에 포함한다. 행이 15개를 넘으면 요청이 과도하게 큰 것이므로 분할을 제안한다 |
| 배경 | 왜 바꾸는가 — 기존 구조와 문제, 변경 후 구조 비교, 프로젝트 고유 용어 풀이. 방향 합의를 생략했으면 대안이 하나뿐인 근거 | 구현 중 분기 판단에 쓰이는 것만. 없으면 `해당 없음` |
| 구현 계약 | 추가·변경되는 계약만 before/after — 프로젝트 사실 `계약`의 종류별로: 외부 인터페이스(엔드포인트·스키마)와 새로 쓰는 필드의 귀착지 / 공개 모델 필드 / 진입점·인자·복귀 경로 / 공용 시그니처 | 그대로인 항목은 적지 않는다. 실패 시 어떤 결과가 되는지는 적는다. 계약 종류가 많으면 이 절 안에서 하위 제목으로 나눈다 |
| 화면 구성 | 요소별 재사용·확장·신규 판정과 근거, 시안 링크 하나 | 재사용 판정은 대상 파일을 열어 시그니처를 확인한 뒤 적는다. 화면에 실제로 있는 상태(로딩·빈·에러·권한)만 적는다. UI 변경이 없으면 `해당 없음` |
| 적용 범위 | 바뀌는 모듈·기능 묶음과 묶음별 변경 한 줄, 그리고 비목표 | 파일 경로는 적지 않는다(실행 절). 비목표에는 이번 변경에 필요 없는 인접 정리·리팩터링을 적어 배제한다. 손대는 코드 자체의 결함이 작업을 막으면 배제하지 말고 범위에 넣는다 |
| 기존 동작 보존 | 이 변경 후에도 바뀌면 안 되는 동작 목록 | 리팩터링·구조 변경이면 반드시 쓴다. 신규 기능이라 보존할 동작이 없으면 `해당 없음` |
| 테스트 케이스 | 행동 그룹별로 `테스트명(프로젝트 테스트 문서의 함수명 형식) — 입력 — 기대 결과` 한 줄씩. 단위 테스트로 검증할 수 없는 조건은 실행해야 보이는 동작(외부 SDK·기기 상태)이면 `수동 확인: <확인 절차>`, 코드를 읽으면 판정되는 구조(분기 유무·호출 순서)면 `리뷰 확인: <항목>` 한 줄 | ⑥이 test-engineer에 그대로 넘기고, 수동 확인 줄은 ⑥ 완료 보고에, 리뷰 확인 줄은 ⑤ 위임 메시지에 옮긴다. `수용 조건`·`기존 동작 보존`의 행마다 케이스나 확인 줄이 있어야 한다. 단위 테스트 대상 코드 변경이 없으면 `해당 없음` |
| 고려한 대안 | 검토했으나 버린 안과 이유, 리뷰 발견 중 반영하지 않은 것과 이유 | 채팅 방향 합의에서 버린 접근을 포함한다. 검토자가 "왜 이걸 안 했나"를 보는 자리다 |

### 실행 절

| 절 | 내용 | 판정 기준 |
|---|---|---|
| 작업 순서 | 독립적으로 검증 가능한 단계마다 — 할 일, 파일 표(경로 / 신규·수정 / 할 일), 검증 명령, 커밋 경계 | 앞 단계가 만들지 않은 것을 뒤 단계가 쓰면 구현 계약 절이 빠진 것이다. 모듈 경계를 넘는 파일이 빠지지 않았는지 확인한다. 컴파일이 함께 깨지는 변경은 한 커밋으로 묶는다고 적는다 |
| 회귀 대상 | 공용 파일을 고칠 때 함께 확인할 기존 호출부 | 공용 컴포넌트·모델·네비게이션 규약을 건드리면 반드시 적는다. 인터페이스를 늘리면 구현체와 테스트 대역(fake·stub)을 grep으로 확인해 있는 것만 적는다 — 추정으로 행을 만들지 않는다 |
| 참조 문서 | 프로젝트 사실의 문서 항목(`코드 스타일`·`아키텍처`·`테스트 문서`) 중 관련 문서와 절 | 구현 단계가 이 목록을 읽는다. 없으면 `해당 없음` |

## 템플릿

```markdown
# <작업명>

**작성일**: YYYY-MM-DD

## 설계
### 한눈에 보기
### 동작 원리
### 수용 조건
| 상황 | 결과 |
|---|---|
### 배경
### 구현 계약
### 화면 구성
### 적용 범위
### 기존 동작 보존
### 테스트 케이스
### 고려한 대안

---
자기 대조(설계): …

## 실행
### 작업 순서
### 회귀 대상
| 고치는 것 | 확인할 기존 동작 |
|---|---|
### 참조 문서

---
자기 대조(실행): …
```

## 자기 대조

계획을 쓴 직후, 사용자에게 제시하기 전에 작성자가 수행한다. 계획에 대한 유일한 사전 검증이므로 생략하지 않는다.

**구현 단계에서 실제로 문제를 일으키거나 사람이 읽고 이해하지 못할 것만 지적으로 본다.** 계약이 빠졌거나, 서로 모순되거나, 해석이 갈려 다른 것을 만들게 될 문장, 그리고 작성 선의 가독성 규칙을 어긴 줄이 지적이다. 취향 차이는 지적이 아니다.

지적은 제시 전에 고친다. 고칠 수 없는 것(사용자 답이 필요한 것)만 제시에 함께 낸다.

**설계 항목** — 설계 절을 쓴 뒤 제시 전에 대조한다.

- `한눈에 보기`와 `동작 원리`만 읽고 변경을 설명할 수 있는가. 프로젝트 고유 용어·심볼이 풀이 없이 처음 나오지 않는가.
- 기호 나열이나 약칭으로 압축한 줄이 없는가. 한 줄에 정보가 둘 이상 몰려 있지 않은가.
- 같은 규칙·결정이 두 절 이상에 반복되지 않는가.
- `수용 조건`의 행마다 그것을 일으키는 입력과 결과가 `구현 계약`의 계약으로 표현돼 있고, 실패 경로 행이 있는가. 미확정 행이 `미확정`으로 표시돼 있는가.
- `수용 조건`·`기존 동작 보존`의 행마다 테스트 케이스 또는 `수동 확인`·`리뷰 확인` 줄이 있는가. 케이스는 `테스트명 — 입력 — 기대` 형식으로 한 줄씩인가(여러 케이스를 한 줄에 압축하면 ⑥이 그대로 구현할 수 없다). 검증 방법이 없는 행은 `고려한 대안`으로 옮긴다.
- `구현 계약`의 각 공개 모델 필드에 출처와 초기값이 적혀 있는가. `TBD`·"적절히 처리" 같은 미룸이 남지 않았는가.

**실행 항목** — 실행 절을 쓴 뒤 제시 전에 대조한다.

- `작업 순서`의 파일 표가 `구현 계약`을 전부 덮는가.
- 단계 간 의존 역전이 없는가 — 앞 단계가 만들지 않은 것을 뒤 단계가 쓰지 않는가.
- 파일 표에 리터럴 코드가 있는가 — 설계에 문장으로 있는 것을 코드로 다시 쓴 것 포함. 함정 경고(왜 그렇게 해야 하는지)는 코드가 아니므로 남긴다.
- 회귀 대상·파일 표의 각 행이 설계 단계에서 열어 본 것인가. 확인하지 못한 행은 `미확인`으로 적고 미해결로 낸다 — 실행 단계에서 새로 탐색하지 않는다.

### 결과 보고

각 단계의 자기 대조를 마치면 결과를 해당 절 끝의 `---` 아래에 적는다(템플릿 위치). 설계 블록은 설계 제시 시, 실행 블록은 실행 제시 시 추가한다.

```
자기 대조(설계|실행): 통과 | 미해결 있음 (대조 N/N)
- 고침: [절 이름], [절 이름]
- 미해결 [절 이름]: 무엇이 비었는지 — 구현 단계에 어떤 문제가 되는지 / 사용자에게 무엇이 필요한지
```

`N/N`은 대조한 항목 수와 해당 단계 목록의 전체 항목 수다 — 분모에 못 미치면 대조를 마치지 않은 것이다. 고친 항목은 절 이름만 적고 내용은 적지 않는다. 계획을 제시할 때 응답에는 미해결 항목만 옮긴다 — 미해결이 없으면 자기 대조를 응답에 내지 않는다.

## 검증

- 자기 대조 수행: 계획 파일에 설계·실행 블록이 각각 있고 `N/N` 분모가 해당 단계 체크리스트 항목 수(설계 6, 실행 4)와 일치하는지 확인한다.
- 가독성: 계획 파일의 `한눈에 보기`·`동작 원리`를 프로젝트를 모르는 사람 기준으로 읽어, 심볼이 풀이 없이 나오거나 기호 나열로 압축한 줄이 없는지 확인한다.
- 중복: 같은 결정이 `수용 조건` 밖의 절에 다시 적히지 않았는지 확인한다.
- 자족성: 이 계획 파일과 요청 원문만으로 구현 착수가 가능한지 — 포인터만 있고 내용이 없는 절이 남았는지 확인한다.
- 미룸: "구현 시 확인·구현 시 결정"으로 남긴 항목이 지금 결정할 수 없는 것인지 확인한다. 문서를 읽거나 코드를 보면 정해지는 것을 미뤘으면 계획 단계에서 정한다.
