# merge

목적: 지정된 브랜치들을 목적지 브랜치에 병합하고 게이트를 통과시킨다.

## 절차

1. **입력 확인**: 병합할 브랜치들과 목적지 브랜치를 입력에서 받는다. 없으면 묻는다 —
   - 병합 대상: 로컬 브랜치 목록(`git branch`)을 선택지로 제시 (복수 선택).
   - 목적지: 로컬 브랜치 목록 + 자유 입력을 선택지로 제시.
2. **목적지 준비**: 기존 브랜치면 checkout, 새로 만들면 `release`에서 분기한다.
3. **브랜치별 사전 검사**: 대상 브랜치마다 게이트 1~5를 병합 전에 실행한다. 차단 항목에 걸린 브랜치는 병합하지 않고 제외한다. 보고 항목은 결과를 기록하고 진행한다.
4. **병합**: 사전 검사를 통과한 브랜치를 순서대로 병합한다. 충돌 시 아래 기준으로 해결을 시도하고, 해결 내역(파일·선택·근거)을 보고해 사용자 확인을 받은 뒤 커밋한다.
5. **통합 검사**: 병합이 끝난 통합 브랜치에서 게이트 6~8을 순서대로 실행한다.
6. **통합 검사 실패 시**: 원인 브랜치를 특정해 그 병합을 되돌려 제외하고 통합 검사를 재실행한다. 통합 브랜치에서 원인을 직접 수정하지 않는다.
7. **보고**: 병합된 브랜치, 제외된 브랜치와 사유, 게이트 결과 표(항목·판정·상세).

## 게이트

판정은 **차단**(브랜치 제외 사유)과 **보고**(결과에 적고 진행)로 나뉜다. 비교 기준은 `release`다 — 목적지가 다른 브랜치면 그 브랜치로 바꾼다.

### 브랜치별 사전 검사

| # | 항목 | 판정 방법 | 판정 | 근거 |
|---|---|---|---|---|
| 1 | 커밋 제목 형식 | `git log release..<branch> --format=%s`의 모든 줄이 `^(Feat\|Fix\|Refactor\|Chore\|Docs\|Test): `에 매치 | 보고 — 위반 커밋 목록 | CLAUDE.md 커밋 규칙 |
| 2 | impl 간 직접 의존 없음 | 변경된 `feature/*/impl/build.gradle.kts`에 `projects.feature.<x>.impl` 참조가 없음 | **차단** | `docs/ARCHITECTURE.md` 모듈 구조 |
| 3 | TeamMatch 미변경 | `git diff --name-only release..<branch> -- feature/team-match`가 비어 있음 | 보고 — 변경 파일 목록과 "삭제 예정 모듈" 경고 | TeamMatch 삭제 예정 결정 |
| 4 | 잔류물 없음 | `git diff release..<branch> -- '*.kt'`의 추가 줄(`+`)에 `Log.d(`·`Log.v(`·`println(`·`TODO`·문자열 리터럴 안의 `http://`·`https://`가 없음 | 보고 — 파일:라인 목록 | 기존 동작(디버그 출력·하드코딩 URL은 `BuildConfig`·리소스로) |
| 5 | 화면 로깅 등록 | diff에서 추가된 `entry<…NavKey>` 블록마다 `LogScreenView` 또는 `logScreenView` 호출이 있음. 새 `ScreenName` 상수가 추가됐으면 이벤트 정의 시트 등록 여부를 사용자에게 확인 요청 | 보고 — 누락 entry 목록 | `docs/ANALYTICS.md` 빠른 시작 |

### 통합 검사

| # | 항목 | 판정 방법 | 판정 |
|---|---|---|---|
| 6 | 빌드 | `./gradlew assembleDebug` | **차단** |
| 7 | 테스트 | `./gradlew test --continue` | **차단** |
| 8 | 문서 정합성 | docs-sync에 병합 변경 범위 위임 | 보고 — 규범 위반·하네스 불일치는 docs-sync 보고 그대로 |

## 충돌 해결 기준

- 원칙: 양쪽 브랜치의 의도를 모두 보존한다. 근거 없이 한쪽을 폐기하지 않는다.
- 서로 독립인 변경이 같은 지점에 겹침 → 둘 다 반영한다.
- 같은 대상을 다르게 바꿈 → 각 브랜치의 커밋 메시지·변경 맥락으로 의도를 대조해 판단한다. 판단이 서지 않으면 사용자에게 묻는다.
- 한쪽 수정 vs 한쪽 삭제 → 삭제한 브랜치의 의도를 확인해 판단한다. 애매하면 사용자에게 묻는다.
- 버전·자동 생성 파일 → 목적지 기준 최신 값을 취하거나 재생성한다.
- 해결 후 컴파일 확인을 거친 뒤 커밋한다.

## 경계

- 대상: 로컬 브랜치 병합과 게이트 수행.
- 비대상: 원격 push, 배포, 게이트 실패 원인 코드의 수정, 보고 항목의 수정.

## 종료 조건

차단 게이트를 통과한 상태로 병합 결과와 게이트 결과 표를 보고하면 완료. 원인 브랜치를 제외한 경우도 그 사유를 보고했으면 완료.

## 실패 시

목적지 준비가 불가능하거나, 제외를 반복해도 통합 검사가 실패하면 멈추고 상태를 보고한다.

## 검증

- (시험) 호출: `/merge`로만 실행되고 일반 대화의 "병합" 언급에 발동하지 않는지 확인한다.
- (시험) 목적 달성: 대표 병합 1회를 수행해 게이트 순서·충돌 확인 절차·보고 형식이 지켜지는지 확인한다.
- (시험) 차단: `feature/*/impl/build.gradle.kts`에 다른 impl 의존을 넣은 브랜치를 대상에 포함해 병합 없이 제외되는지 확인한다.
- (시험) 보고: 제목 형식이 틀린 커밋을 가진 브랜치를 대상에 포함해 병합은 되고 결과 표에 위반 커밋이 나오는지 확인한다.
- 명령: 통합 검사 명령 두 개가 이 리포에서 유효한지 확인한다.
